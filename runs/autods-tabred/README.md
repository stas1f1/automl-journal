# Перепрогон AutoDS-Tools на общем адаптере TabReD

Цель — вернуть AutoDS в главную таблицу статьи. Сейчас его числа по TabReD
посчитаны на другом срезе данных, чем у FEDOT.LLM и Terminus-2, и потому
несопоставимы ни с ними, ни с опубликованными бейзлайнами.

| | срез | reward |
|---|---|---|
| `harbor-tabred-adapter` (Terminus-2, FEDOT.LLM) | полные официальные сплиты | AUC / `1/(1+RMSE)` |
| `harbor-datasets-tabred` (прежние прогоны AutoDS) | хвост теста ~24 %, + колонка `timestamp` | AUC / `max(0, R²)` |

После этого прогона все три системы окажутся на одних данных.

## Что нужно один раз

1. **Секрет.** `cp env.example env.local`, вписать `AUTODS_API_KEY`.
   Файл в чат не показывать и не коммитить.
2. **Kaggle.** `~/.kaggle/kaggle.json` уже на месте. Пакет `tabred` тянет
   препроцессенные данные с Kaggle; для датасетов из соревнований
   (`homecredit-default`, `homesite-insurance`, `sberbank-housing`) нужно
   один раз принять правила соревнования в браузере под тем же аккаунтом.
3. **Docker** должен быть запущен — Harbor собирает окружение задачи в контейнере.

## Запуск

```bash
./run.sh prepare     # склонировать адаптер и собрать 8 задач из данных Kaggle
./run.sh smoke       # одна задача, одна попытка — проверить, что всё сходится
./run.sh full        # все 8 задач, 3 попытки
```

Результаты лягут в `jobs/`. Метрики в полной точности — в
`<trial>/verifier/reward.json`.

## Перенос чисел в статью

`reward.json` даёт `roc_auc` и `rmse` в сыром масштабе цели — ровно то, что
нужно. Вписать их в словарь `AGENTS` в `paper/make_tables.py`, прогнать
`python3 make_tables.py`, пересобрать статью.

## Грабли, на которые уже наступили

Всё перечисленное уже учтено в `run.sh` и `env.example`; список — чтобы не
разбираться заново.

1. **Формат `.env`.** `KEY = value` с пробелами вокруг `=` не является
   присваиванием для shell — `source` на таком файле падает. Только `KEY=value`.

2. **Коллизия имён CLI.** Адаптер и PyPI-пакет `tabred` объявляют консольный
   скрипт с одинаковым именем; в venv побеждает пакет, и `uv run tabred` из
   README адаптера печатает справку вместо сборки задач. Зовём модуль напрямую:
   `uv run python -m tabred_adapter.main`.

3. **Правила соревнований Kaggle.** `homecredit-default`, `homesite-insurance`
   и `sberbank-housing` не скачаются, пока правила не приняты в браузере под тем
   же аккаунтом, что и `kaggle.json`. Сборка при этом падает целиком, а не
   пропускает эти три задачи.

4. **`AUTODS_C1_DISABLED` по умолчанию выключен, то есть слой ПРИМЕНЯЕТСЯ.**
   «Из коробки» агент всегда идёт веткой C1; базовую надо запрашивать явно.

5. **Разные соглашения о рабочем каталоге у двух адаптеров.** Это была причина
   первого зависшего прогона:

   | | данные | посылка | рабочий каталог агента |
   |---|---|---|---|
   | `harbor-tabred-adapter` | `/app/data` | `/app/predictions.csv`, одна колонка `target` | `/app` |
   | `harbor-datasets-tabred` | `/workspace` | `/workspace/submission.csv`, `id,target` | `/workspace` |

   У `AutoDSAgent` в коде зашит `DEFAULT_WORKSPACE = "/workspace"`, поэтому на
   этом адаптере он видел пустой каталог и вставал молча — с нулевым логом.
   Лечится `--ak workspace=/app`. Инструкция задачи самодостаточна: она сама
   говорит агенту, где данные и куда писать.

6. **Осторожно с `pkill -f`.** Шаблон вроде `pkill -f "harbor run"` совпадает с
   самой командой, в которой он написан, и убивает собственную оболочку.

## Версия слоя C1

Замеры объёма надо делать по версии с HuggingFace, а не по той, что лежит в
форке на GitHub — они разные. Опубликованная состоит из ТРЁХ блоков:

```
instruction + "\n\n" + _LIBRARY[family] + "\n" + _HARDWARE + _DISCIPLINE
```

| блок | символов | меняется с модальностью |
|---|---|---|
| `_LIBRARY` | 359–1291 | да |
| `_HARDWARE` | 670 | нет |
| `_DISCIPLINE` | 3122 | нет |

Суммы сходятся с `DATA_SOURCES.md` до символа. Предписание инструмента — от
8.6 % до 25.4 % слоя; остальное это фиксированный блок про устройство вычислений
и дисциплина обучения.

## Отложено

**Общий обогащённый образ для всех трёх систем.** Сейчас специализированные
библиотеки доставлены только в ветку AutoDS — это восстанавливает условие её
опубликованных прогонов. Данные у всех трёх систем совпадают, состав окружения
нет.

Приоритет низкий, делаем только при двух условиях: осталось время И AutoDS с
библиотеками обошёл Terminus-2. Если AutoDS и с ними позади, ось перестаёт быть
несущей: остаточное преимущество достаётся именно ему и работает против нашего
собственного вывода, то есть текущий порядок систем консервативен.

Откат образов к штатному: `python3 autods_dockerfile.patch.py --revert`.

## Smoke-прогон 28.08.2026

`cooking-time`, одна попытка, образ с LightAutoML на Python 3.12, `--ak workspace=/app`.

```
RMSE 0.4819824839149808   reward 0.6747718079354631   53 мин 52 с
```

Для сравнения на тех же официальных сплитах: Terminus 2 — 0.48373, настроенный
XGBoost из статьи TabReD — 0.4823, лучший опубликованный метод — 0.4806.
То есть на этой задаче AutoDS с общим адаптером обходит и открытый харнесс, и
бустинг. Это ровно то условие, при котором отложенная рука с общим образом
становится нужной; но одна задача — ещё не вывод, ждём все восемь.

Практическая оценка времени: около 50 минут на испытание, `full` это 8 задач ×
3 попытки при `-n 2` — порядка десяти часов. Планировщик AutoDS сам закладывает
бюджет 4–6 часов, упирается в часовой таймаут LightAutoML.

## Что нужно, чтобы развести K_tool и K_disc (эксперимент 4)

Слой приходит одним куском, поэтому ни одна строка абляции сейчас не относится
ни к предписанию инструмента, ни к дисциплине обучения по отдельности. Чтобы
развести, нужно четыре вещи — все до запуска, ни одну нельзя сделать на ходу.

1. **Привести форк к опубликованной версии.** В форке `florentiner/AutoDS-Tools`
   ветка `mlab-gpu-pub` — устаревшая ревизия: в ней нет блока `_HARDWARE`,
   который есть в версии на HuggingFace и который входит в состав слоя
   (670 знаков на каждой задаче). Патч, написанный против форка, разведёт не то,
   что реально применялось в опубликованных прогонах.
2. **Разбить `augment()` на независимо переключаемые половины** в
   `apps/harbor/src/autods_harbor/c1_prompt.py`, сохранив побайтово тот же
   результат при обоих включённых флагах. Блок `_HARDWARE` — третья категория,
   не инструмент и не дисциплина; решить, к какой руке он едет, и записать
   решение, иначе 2×2 окажется 2×2×2.
3. **Добавить `AUTODS_K_TOOL_DISABLED` и `AUTODS_K_DISC_DISABLED`** рядом с
   существующим `AUTODS_C1_DISABLED` в `agent.py`.
4. **Запушить ветку.** `run.sh` ставит агента по
   `git+…@$AUTODS_BRANCH`, то есть берёт код с удалённой ветки, а не локально.
   Пуш меняет то, что установится в следующих испытаниях, поэтому делать его
   во время идущего прогона нельзя, и он требует отдельного согласия.

Локальный чекаут `~/Documents/GitHub/AutoDS-Tools` сейчас на ветке
`grad-updates` с несохранёнными изменениями — это рабочее дерево, трогать его
не следует; для патча нужен отдельный клон.

## Рука с общим образом — готова к запуску

`run.sh matched` запускает Terminus 2 через тот же адаптер, те же данные и те же
скореры. Смысл целиком зависит от того, в каком состоянии образы:

| состояние образов | что измеряет `matched` |
|---|---|
| пропатчены (`autods_dockerfile.patch.py` без `--revert`) | **рука с общим образом**: обеим системам доступны одни библиотеки, различается только архитектура |
| откачены (`--revert`) | воспроизведение прежнего условия на штатном образе |

Порядок важен: `--revert` до запуска `matched` молча уничтожает саму руку.
Сначала `matched`, потом откат.

Имя агента `terminus-2` проверено против установленного harbor
(`harbor.agents.terminus_2.Terminus2.name()`). Стоимость: Terminus 2 занимал
около 5 минут на испытание, то есть 24 испытания при `-n 2` — примерно час,
против десяти часов у AutoDS. Запускать одновременно с идущим прогоном нельзя:
LightAutoML держит четыре ядра, обе телеметрии по времени станут негодными.

Условие из брифа — «доделаем, если AutoDS обгонит Terminus 2 после
провизионирования» — по первым трём задачам выполняется: `cooking-time`
0.48198 против 0.48373, `ecom-offers` 0.58000 против 0.55850, `weather`
1.47913 против 1.52324. Решение о запуске — за автором.

## `trace_stats.py`

Диагностика по нашим собственным трейсам: какую модель агент заявил, какую
валидационную оценку он себе намерил, что показал верификатор, разрыв между
ними, число шагов и следы починки.

```bash
python3 trace_stats.py jobs --only=full
```

Разрыв «валидация → тест» — главная величина: сплиты TabReD временные, поэтому
он показывает, сколько от собственной оценки агента переживает сдвиг. На
`cooking-time` это +0.018 RMSE в обоих прогонах (0.464 против 0.482), то есть
агент систематически оптимистичен к себе примерно на четыре процента.

Побочно виден разброс усилий: `cooking-time` решается за 21–24 шага,
`ecom-offers` — за 139.

## Рука без слоя предписанного знания

`run.sh nolayer` — тот же AutoDS, тот же адаптер, тот же образ, но
`AUTODS_C1_DISABLED=1`. Разность `full` минус `nolayer` и есть цена слоя на
общих данных, без примеси провизионирования и архитектуры.

Слой собирается на хосте до старта контейнера (в `trial.log` строка
`AutoDS C1 layer applied (family=…)` появляется раньше команды запуска агента),
поэтому экспорта переменной на хосте достаточно. **Обязательно проверить после
старта:** в `trial.log` этой строки быть не должно. Если она там есть — прогон
не тот, за который себя выдаёт, и сравнивать его нельзя.

```bash
grep -L 'C1 layer applied' jobs/autods-tabred-nolayer-*/*/trial.log
```

### Почему это вообще нужно

В таблицу лидеров каждая система входит в своей штатной конфигурации:
Terminus 2 получает только постановку задачи, FEDOT.LLM — конвейер с вваренным
выбором инструмента, AutoDS — постановку плюс свой слой. То есть строка таблицы
сравнивает системы как они поставляются, а не архитектуры как таковые. Две руки
разводят нити: `nolayer` снимает предписание, `matched` снимает
провизионирование. Каждая — один проход по тем же восьми задачам.

## Что сделать, когда прогон закончится

1. `python3 collect.py jobs --only=full` → вставить строку `"AutoDS-Tools": [...]`
   в `AGENTS` в `paper/make_tables.py`.
2. `python3 collect.py jobs --only=full --attempts` → вставить словарь в
   `AUTODS_ATTEMPTS` там же; таблица шума сама отрисует второй блок и пересчитает
   число побитовых совпадений в подписи.
3. `python3 compare_terminus.py` → взять собственный порог шума AutoDS **по худшей
   задаче**, не по медиане: на `weather` разброс на порядок больше, чем на
   `ecom-offers`, единого числа нет.
4. Добавить в `result_files/MASTER_all_systems.csv` новые строки как отдельный
   вариант (`common adapter`), не трогая старые: те остаются с пометкой о
   несопоставимости, и обе версии нужны, потому что разница между ними — это и
   есть измеренная цена подготовки данных.
5. `cd ../../paper && python3 make_tables.py && latexmk -pdf main.tex`.
6. Обновить `\pending`/`\todo` в разделах 5, 6 и 11: перепрогон состоялся.


## `libgomp1`: сломанный рантайм в нашем же образе

Обогащённый образ ставит `lightautoml`, а тот тянет `lightgbm` колесом. Колесо
не несёт `libgomp.so.1`, рантайм OpenMP, а `python:*-slim` его не содержит.
Импорт при этом проходит: библиотека грузит `.so` через `dlopen` уже при
обращении. Падение случается внутри `fit_predict`, на стадии чтения данных, и
выглядит как `BrokenProcessPool` от joblib — то есть как сбой моделирования,
которым не является.

Задело 22 из 24 испытаний руки `full` и 8 из 10 первых испытаний руки с общим
образом. Все чинились сами командой `apt-get update && apt-get install -y
libgomp1`. Цена починки: медианно один шаг из 22 и прерванная стадия чтения,
до обучения.

Два испытания, упёршихся в потолок, до этого места не дошли, так что таймауты
багом не объясняются. Но время починки сидит внутри длительности всех
остальных, и отделить его без исправленного прогона нельзя.

`autods_dockerfile.patch.py` теперь ставит `libgomp1` вместе с `git`. Следствие
для плана: ячейки сетки 2x2 сравниваются при собственном шуме AutoDS около
0.1%, поэтому все четыре обязаны идти на одном образе. Значит, ячейку «обе
половины включены» (`full`) надо переснять на исправленном образе, а не
достраивать сетку вокруг старой.

## Проверки, которые стоит гонять до, а не после

- `./run.sh verify` — отпечаток слоя, который реально применится (табличный:
  4972 символ, sha `a58b4d40678ff1aa`), и по каждому заданию число испытаний,
  где слой применялся. Слой собирается **на хосте**, копией пакета из venv
  инструмента harbor, а не той, что pip ставит в контейнер. Поэтому повторный
  `prepare` со свежим клоном молча меняет условие эксперимента, ничего не меняя
  в видимой конфигурации.
- `python3 walltime.py --only=<job>` — длительность испытаний по меткам файлов
  (`agent/instruction.md` → `verifier/reward.json`), число испытаний у потолка и
  готовый список для `RERUN_MINUTES`.
- `python3 enable_halves.py` — переносит флаги `AUTODS_K_TOOL_DISABLED` и
  `AUTODS_K_DISC_DISABLED` в исполняемую версию, не трогая текст слоя. Проверяет
  себя по тому же sha и откатывается сам, если слой сдвинулся. `--revert`
  возвращает однофлаговую версию из бэкапов `*.single-flag`.
- `python3 compare_terminus.py --only=<job> --label=<имя> --noise=<порог>` —
  сравнение с опубликованными числами Terminus-2. Для двух разных систем порог
  берётся по более шумной (1.0%); для конфигураций одной системы нужен её
  собственный, по худшей задаче, и его надо задать явно.
- `python3 compare_runs.py --a=<job> --b=<job> --noise=<порог>` — сравнение двух
  прогонов одной системы, то есть ячеек сетки между собой. Порог тут около 0.1%,
  а не 1.0%: обе стороны — один и тот же AutoDS, и брать более шумную из пары
  нечего. Сорванные испытания исключаются из обеих сторон и называются отдельно.


## Прогон на сервере nss-calc2

18 ядер, 94 ГБ памяти, без GPU. Локальная машина уступает не скоростью одного
испытания (35.2 минуты против 36.5), а тем, сколько их идёт разом: на сервере
четыре против двух.

Каталог: `/var/essdata/s_chumakov/automl-journal`. Системный раздел там всего
40 ГБ, поэтому всё лежит на сетевом `/var/essdata`.

### Что пришлось починить, чтобы это заработало

- **Прокси.** OpenRouter с сервера напрямую отдаёт 403, через `LLM_PROXY` — 200.
  Всё остальное (PyPI, GitHub, Docker Hub, Debian) доступно напрямую, поэтому в
  `NO_PROXY` перечислено всё, кроме модели. Главное: вызовы к модели делает
  агент **изнутри контейнера**, а туда попадает только фиксированный список
  переменных, и прокси в нём не было. Добавляет `enable_proxy.py`.
- **apt в контейнере.** При загрузке пакетов apt сбрасывает права на служебного
  пользователя `_apt`, у которого здесь не работает разрешение имён; сборка
  падала с `Temporary failure resolving`. Лечится строкой
  `APT::Sandbox::User "root"` в образе — она меняет, от кого качается, а не что
  ставится, и на локальной машине безвредна.
- **Кавычки в `.env`.** Значение с символом `<` оболочка принимает за
  перенаправление ввода. `run.sh` читает файл через `. `, да ещё под `set -e`,
  так что незакавыченное значение роняет запуск целиком.

### Место на диске: главная ловушка

Данные задач копируются **внутрь** образов (`COPY data/`), а их 6.2 ГБ.
`docker info` показывает `Docker Root Dir` на сетевом разделе, но фактически
образы лежат в хранилище containerd на `/mnt/containerd`, 196 ГБ. Проверять
надо именно его.

Четыре одновременные сборки с холодного кэша заняли остаток раздела и забили
его до нуля, чем сломали Docker всей машине. Порядок, который этого избегает:

1. `df -h /mnt/containerd` — убедиться, что свободно хотя бы 40 ГБ;
2. собрать один образ вручную (`docker build` в каталоге любой задачи), чтобы
   прогреть общий базовый слой: установка LightAutoML занимает около пяти минут
   и иначе повторится восемь раз;
3. только потом запускать серию с `HARBOR_CONCURRENCY=4`.

`docker builder prune -a` освобождает кэш сборки без потери образов и данных —
это первое, что стоит сделать при нехватке места.

### Параллельность

`HARBOR_CONCURRENCY` задаёт число одновременных испытаний (по умолчанию 2).
Одно испытание занимает около четырёх ядер и 2.7 ГБ при лимите контейнера в
16 ГБ, так что на 18 ядрах разумный потолок — четыре.

**Это часть измерения, а не настройка удобства.** Время испытания статья
приводит как результат, поэтому во всех сравниваемых вариантах параллельность
обязана совпадать и называется вместе с числами.

### Половины слоя на сервере

В серверной установке `autods_harbor` механизм половин уже присутствует:
`augment` принимает `tool=` и `discipline=`, агент читает
`AUTODS_K_TOOL_DISABLED` и `AUTODS_K_DISC_DISABLED`. Резервных копий
`*.single-flag` рядом нет, то есть это не результат `enable_halves.py`, а уже
собранная версия. Запускать там заплатку не нужно и не следует.

Проверено, что это не подменяет лечение: отпечаток слоя при обеих включённых
половинах — 4972 символ, sha `a58b4d40678ff1aa`, ровно как во всех прогонах
статьи. Именно ради этого равенства separators в `enable_halves.py` писались
байт в байт, и именно его надо перепроверять после любого касания пакета,
а не версию или тег.

Пути к пакету больше не привязаны к `python3.13`: локально стоит 3.13,
на сервере 3.12. И `run.sh verify`, и `enable_halves.py` теперь ищут
`harbor/lib/python3.*/site-packages/autods_harbor`.

Замена `run.sh` на сервере во время серии недопустима: bash дочитывает скрипт
по ходу выполнения, а запустивший серию экземпляр остаётся живым до конца.
Синхронизировать файлы только между прогонами.

## K_disc, скрещенный с Terminus-2

Слой AutoDS собирается на хосте и доходит только до собственного агента. Чтобы
дать тот же текст другой системе, его кладут в саму задачу.

```bash
# 1. собрать набор задач с блоком дисциплины
python3 make_kdisc_tasks.py --check   # печатает длину и sha блока, ничего не пишет
python3 make_kdisc_tasks.py           # datasets/tabred -> datasets/tabred-kdisc

# 2. проба на одной задаче, затем полный проход
./run.sh kdisc-smoke
./run.sh kdisc

# или всё вместе, с проверкой воздействия между шагами
HARBOR_CONCURRENCY=4 nohup ./kdisc.sh &
```

`make_kdisc_tasks.py` читает `_DISCIPLINE` из **установленного** пакета
`autods_harbor`, а не из клона рядом — это тот же байтовый источник, из которого
слой попадает в основные прогоны. Блок дописывается как
`base.rstrip() + "\n\n" + disc`; задания растут с 1040–1076 до 4720–4756
символов.

**Как проверять, что воздействие дошло.** У Terminus-2 в каталоге испытания нет
`instruction.md` — задание видно только в `agent/trajectory.json`:

```bash
grep -l "REQUIRED, STRICT" jobs/<задание>/*/agent/trajectory.json | wc -l   # ожидается 24
python3 -c "import json,glob;print(json.load(open(glob.glob('jobs/<задание>/*/config.json')[0]))['task'])"
# {'path': 'datasets/tabred-kdisc/...', 'source': 'tabred-kdisc'}
```

Ранняя версия `kdisc.sh` искала блок в `agent/*.md` и печатала 0. Это значило
«файла нет», а не «блока нет»; строка исправлена.

**Ячейка сравнения** — обычный прогон Terminus-2 на той же модели, машине,
образе и параллельности: `terminus-tabred-Mmid-*`. Ничего дополнительно
запускать не нужно, у Terminus-2 нет своего слоя предписанного знания, поэтому
его штатный прогон и есть контроль.

**Результат** — в `result_files/DATA_SOURCES.md`, раздел «K_disc, скрещенный с
Terminus-2».
