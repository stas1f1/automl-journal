\section{Three architectures as design points}
\label{sec:systems}

We describe each system by the questions that matter for our argument: where a
modelling decision is taken, who can override it, how many execution iterations
are available, and what is fixed beyond the model's reach.

\subsection{FEDOT.LLM: a rigid pipeline}

FEDOT.LLM~\citep{fedotllm} pairs an LLM-driven agent with the FEDOT
framework~\citep{nikitin2022fedot} for tabular tasks, in four stages: data
understanding extracts paths, types, target, metric and submission format;
configuration and code generation produce a task-matched FEDOT configuration and
select a template with fixed input/output contracts, leaving only the
implementation to the model, with helper functions encapsulating correct API
usage; an execution and correction loop runs the code in a sandbox, patching and
re-running until success or an iteration cap; reporting persists the script, the
trained pipeline and the predictions. The decisive property here is that the
choice of modelling tool is not a decision at all but the architecture: the
system cannot solve a task with anything other than FEDOT, and accepts only
tabular inputs.

\subsection{AutoDS-Tools: a multi-agent system}

AutoDS-Tools~\citep{autodstools} coordinates six specialised agents communicating
through structured reports: an Analyst performs exploratory analysis, a Researcher studies the
target library and produces usage cookbooks, a Planner turns both into an
execution plan, a Coder refines the solution against execution results, a
Debugger absorbs execution errors without disrupting the main context, and a
Presenter audits the result. The chain is literal rather than metaphorical---each
stage writes a Markdown report that the next reads, so a trial directory holds
the analyst's, the researcher's and the planner's reports as separate Markdown
artefacts. Freedom of action is broad: any library
in the environment, and restructuring between iterations.

\subsection{Terminus-2: an open harness}

Terminus-2 provides a shell, a working directory and an execution loop, and
prescribes nothing about how the task should be solved. There is no planner, no
role decomposition and no template. The model reads the task statement, inspects
the data, writes code, runs it, reads the output, and repeats until it emits a
submission or exhausts its budget.
