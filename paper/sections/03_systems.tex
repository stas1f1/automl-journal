\section{Three architectures and the prescribed-knowledge layer}
\label{sec:systems}

% STAGE 3: rewritten 8 September 2026.

The three systems are three design patterns of agentic AutoML: a fixed
pipeline that the model configures, a team of specialised agents, and a single
agent in an open execution loop. We describe each by the questions that matter
for the argument: where a
modelling decision is taken, who can override it, how many execution
iterations are available, and what is fixed beyond the model's reach.
Table~\ref{tab:designpoints} summarises the answers and
Figure~\ref{fig:systems} draws them.

\subsection{FEDOT.LLM: a rigid pipeline}

FEDOT.LLM~\citep{fedotllm} pairs an LLM-driven agent with the FEDOT
framework~\citep{nikitin2022fedot} for tabular tasks in four fixed stages:
data understanding extracts paths, types, target, metric and submission
format; configuration and code generation produce a task-matched FEDOT
configuration and fill a template with fixed input and output contracts, so
that only the implementation is left to the model; an execution and correction
loop runs the code in a sandbox and patches it until success or an iteration
cap; reporting persists the script, the trained pipeline and the predictions.
The decisive property is that the choice of modelling tool is fixed by the
architecture: the system can solve a task only with FEDOT, and it accepts only
tabular inputs.

\subsection{AutoDS-Tools: a multi-agent system}

AutoDS-Tools~\citep{autodstools} coordinates six specialised agents by
structured reports: an Analyst performs exploratory analysis, a Researcher
studies the target library and writes usage cookbooks, a Planner turns both
into an execution plan, a Coder refines the solution against execution
results, a Debugger absorbs execution errors without disrupting the main
context, and a Presenter audits the result. Each stage writes a Markdown
report that the next one reads. The system may use any library installed in
the environment and may restructure the solution between iterations.

\subsection{Terminus-2: an open harness}

Terminus-2 provides a shell, a working directory and an execution loop, and
prescribes nothing about how the task should be solved. The model reads the task statement,
inspects the data, writes code, runs it, reads the output, and repeats until it
emits a submission or exhausts its budget.

\subsection{The prescribed-knowledge axis}
\label{sec:axis}

Interventions that supply a system with knowledge it would otherwise have to
derive are usually treated as one thing. In the layer AutoDS-Tools ships with they are two instructions of very unequal
length: which library to use, and how to train and validate. Their combined
gain is smaller than the sum of their separate gains (Sections~\ref{sec:grid}
and~\ref{sec:kdiscterm}).

\begin{description}
  \item[\Ktool{}, tool prescription.] Which class of instrument to reach for: a
        dedicated tabular AutoML library for tabular data, a vision backbone
        library for images, a graph learning library for graphs, a transformer
        library for text. It removes the question of what one normally uses
        for a task of this kind.
  \item[\Kdisc{}, training discipline.] How to train and how to check oneself:
        the validation protocol, the handling of temporal shift, leakage
        checks, and the prohibition of degenerate submissions. It is
        orthogonal to the choice of library.
\end{description}

The split can be measured. The layer AutoDS-Tools ships with is assembled from a library block chosen by
task family and a discipline block. The first section of the discipline block
is a hardware block, which we count separately. The library block carries one
section heading and the discipline block seven, eight in all. We measured the blocks in the source module that assembles the layer and
checked the counts against the instruction each container received. The library
block runs from \layerLibMin{} characters for text to \layerLibMax{} for tabular
tasks; the hardware block is \layerHardware{} characters and the discipline
block \layerDiscipline{} on every task. The tool prescription, the intervention the layer is named
after, accounts for between $\layerShareMin\%$ and $\layerShareMax\%$ of the
text; the discipline block is the largest component on every task. On the
tabular tasks the whole layer runs to \layerTotalTabular{} characters against a
task statement of \layerBaseTask{}, close to 5$\times$ the length of the
problem it is attached to. An ablation that switches the whole layer at once measures all three blocks
together, so an effect ascribed to tool prescription in such an ablation is at
least as likely to come from the hardware and discipline blocks; those two
blocks are identical across modalities, while the reported effects differ by
modality. Sections~\ref{sec:grid} and~\ref{sec:kdiscterm} measure the two
halves separately and together.

Table~\ref{tab:designpoints} places the three systems on this axis. In
FEDOT.LLM itself the tool prescription is the pipeline: every task is solved
through FEDOT, so \Ktool{} is always on. FEDOT.LLM is the end point of the
axis, the system that fixes its tool most rigidly and searches over its
models; Section~\ref{sec:ceiling} places it level with Terminus-2 in average rank
on tabular data, the family FEDOT was built for. \Kdisc{} could in principle
be crossed with every system. We
cross both halves on AutoDS-Tools and Terminus-2, and FEDOT.LLM enters as the
reference point at which \Ktool{} is always on.

\subsection{A prescription presupposes its environment}

Tool prescription is realisable only where the prescribed tool exists, so it
is a property of the environment as much as of the text. The layer tells the
agent that the specialised library is pre-installed and forbids a fallback to
general-purpose estimators. On the benchmark's own image (Python~3.13) the
prescribed tabular library does not build: an agent given the prescription
there writes a correct pipeline, fails at import and scores zero. The
environment is therefore part of the treatment, and Section~\ref{sec:design}
reports the provisioning of each arm.
